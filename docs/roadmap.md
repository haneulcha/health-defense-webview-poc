## 다음 작업 (우선순위 순)

### 1. 밸런스 + 성과 등급 — 가장 먼저

**왜 이게 1번으로 올라왔나**: [D-023](decisions.md#d-023)이 유능감의 무게를 승패에서 **등급**으로 옮겼습니다. 그런데 등급은 코드에 없고, 넣더라도 현재 곡선에서는 봇 기준 웨이브 1~8이 무손실이라 **거의 전원이 만점**입니다. 분포하지 않는 등급은 유능감을 담을 그릇이 못 됩니다. [`game-design.md`](game-design.md) §7이 "밸런스는 이제 선택이 아니라 전제 조건"이라고 적은 것과 같은 이야기입니다.

**이 순서 변경이 무엇을 감수하는가는 [D-030](decisions.md#d-030)에 있습니다.** 요지는 — 이번 튜닝의 목표를 **봇이 판정할 수 있는 것에만 한정**합니다. 사람을 보기 전에는 사람만 알 수 있는 것을 건드리지 않습니다.

**손댈 곳**: `src/content/waves.ts` 의 `hpScale`, `reward`, 스폰 `interval`, `PREPARE_SECONDS`. 그리고 등급은 새로 만듭니다 (남은 체력 기반 — [D-011](decisions.md#d-011)).

**하지 말 것**: 손으로 플레이하며 감으로 조정. `npx vitest run src/core/balance-report.test.ts` 로 격자를 다시 뽑아 판단합니다.

**건드리지 말 것** (관찰 전이므로): 타워 해금 순서, 튜토리얼·안내 문구, 조작 방식, 타일 크기. 전부 사람을 봐야 아는 것들입니다.

**완료 기준**
- 한 판 3~4분 (현재 5분대)
- 봇 격자에서 첫 체력 손실이 웨이브 5~6쯤 (현재 9)
- 봇 격자에서 **등급이 실제로 갈린다** — 전략에 따라 최소 3개 등급이 나온다. 이게 D-023이 요구한 조건이고, 나머지 두 줄보다 중요합니다
- 승리 가능성은 유지 — `campaign.test.ts` 의 양쪽 경계가 그대로 통과

### 2. 플레이 관찰 5명 — 1번이 끝난 뒤

**방법**: 배포 URL을 **테스터 본인 폰**으로 열게 합니다. 데스크톱 마우스 플레이는 배치 UX·가독성·세션 감각이라는 검증 대상 자체를 무효화합니다. 부수 효과로 실기기 5대분 성능 데이터가 따라옵니다.

**구성**: 디펜스 경험자 2~3명, 비경험자 2~3명.

**프로토콜·기록 양식·판정선은 [`fun-harness.md`](fun-harness.md)에 있습니다** (2026-08-14). 아래 항목은 그중 행동 지표(1.3)에 해당하고, 하네스는 여기에 **귀속 질문(1.1)** 을 더합니다. 유능감 척도(1.2)는 원본 문항을 확보하기 전까지 돌리지 않습니다 ([D-029](decisions.md#d-029)). 관찰자가 한 번이라도 설명하면 그 회차가 무효라는 규칙도 거기 있습니다.

**1번이 끝났으므로 귀속 질문은 등급을 향합니다** — *"왜 그 등급이 나왔어요?"*. 하네스 1.1의 "2차 이후" 행이 1차부터 적용됩니다.

**측정할 것**
- 첫 타워를 놓기까지 걸린 시간 — 설명 없이 이해했는가
- 웨이브 3 이전 이탈 여부
- **실패 후 재도전 여부** — 몰입의 가장 정직한 지표
- 어느 웨이브에서 처음 체력을 잃는가
- 노린 칸에 놓였는가 (타일 48 CSS px가 실제 엄지에 맞는지)

**경험자와 비경험자의 피드백은 분리해서 읽습니다.** TD는 세션이 긴 장르라 경험자는 3~4분짜리 판을 "짧다"고 느낍니다. 그건 설계 실패가 아니라 [`game-design.md`](game-design.md) 1절에서 의도적으로 고른 방향입니다. 반대로 비경험자가 "길다"거나 "뭘 해야 할지 모르겠다"고 하면 그건 고쳐야 할 신호입니다. 두 집단의 같은 단어가 반대 뜻입니다. 근거는 [`tower-defense-research.md`](tower-defense-research.md) 6절.

**완료 기준**: 5명분이 [`fun-harness.md`](fun-harness.md) 1.5의 양식으로 기록되고, **기준선이 수립되며**(3.2), 3.1의 세 극단 조건 중 걸린 것이 있는지 판정된다. 1차의 임무는 합격 판정이 아니라 기준선 수립입니다.

### 3. 저사양 안드로이드 실기기 측정 — 기기가 생기면 즉시

**왜 지금 못 하나**: 안드로이드 단말이 없습니다. 이것 하나뿐입니다. 2번의 관찰에 안드로이드 사용자가 섞이면 거기서 일부 얻어집니다.

**방법**: 폰 브라우저로 `배포URL/?perf` 를 엽니다. 계정도, 빌드도, 업로드도 필요 없습니다. Firebase Test Lab은 여러 기종을 자동·반복 측정할 때나 의미가 있고 PoC에는 과합니다.

**측정 절차**
1. 기본값(40/18/8)에서 판정 줄을 읽는다
2. 슬라이더를 **200 / 60 / 40** 으로 올린다 (스프라이트 약 560개 = 목표 규모 상한)
3. **그 상태로 3~4분 방치 후 다시 읽는다** — 발열 스로틀링은 세션 길이가 있어야 나타나고, 데스크톱·에뮬레이터로는 재현 불가

**확인할 것**
- `draws` 가 2에서 안 움직이는지 (오르면 나머지 수치 전부 무효)
- `work p95` 는 평탄한데 `frame p95` 만 오르는지 → GPU fill-rate 병목
- `heap` 평탄 여부
- 시작 직후 대비 3분 뒤 `work p95` 차이

**완료 기준**: 실기기 기준 `(엔티티 수 → p95)` 표가 `m0-measurements.md` 에 들어가고, 연출 상한이 확정된다.

**실패 시**: 내부 해상도를 먼저 낮추고, 그래도 안 되면 파티클 수를 줄입니다. 아트 방향은 마지막에 건드립니다.

- ~~**건강 데이터 연동을 언제 붙일 것인가.**~~ 나중 문제가 아니라 설계의 전제로 올라갔습니다 (2026-08-12). 이 게임은 헬스케어 제품 안의 기능이고, 인풋(앱 자원 → 게임 전력)과 아웃풋(게임 결과 → XP·포인트)이 게임 구조를 결정합니다. [`game-design.md`](game-design.md) 참조. 구현은 여전히 `src/platform/webview.ts` 자리만 있습니다.
- **맵을 하나로 갈 것인가.** 현재 경로 1개 고정입니다. 리플레이성을 원하면 맵 추가가 가장 싼 레버입니다.
- **저장/진행도.** 없습니다. 매번 처음부터입니다.
