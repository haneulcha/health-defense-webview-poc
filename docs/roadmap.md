## 다음 작업 (우선순위 순)

### 1. 플레이 관찰 5명 — 가장 먼저

**왜 지금**: 나머지 튜닝이 여기에 달려 있습니다. 현재 난이도 곡선은 제가 만든 스크립트 봇 기준이고, 봇은 매번 최적 위치에 배치합니다. 사람이 실제로 어디서 막히는지 보기 전에 밸런스를 만지면 존재하지 않는 문제를 튜닝하게 됩니다.

**방법**: 배포 URL을 **테스터 본인 폰**으로 열게 합니다. 데스크톱 마우스 플레이는 배치 UX·가독성·세션 감각이라는 검증 대상 자체를 무효화합니다. 부수 효과로 실기기 5대분 성능 데이터가 따라옵니다.

**구성**: 디펜스 경험자 2~3명, 비경험자 2~3명.

**측정할 것**
- 첫 타워를 놓기까지 걸린 시간 — 설명 없이 이해했는가
- 웨이브 3 이전 이탈 여부
- **실패 후 재도전 여부** — 몰입의 가장 정직한 지표
- 어느 웨이브에서 처음 체력을 잃는가 (봇은 9웨이브. 사람은 훨씬 이를 것)
- 노린 칸에 놓였는가 (타일 48 CSS px가 실제 엄지에 맞는지)

**경험자와 비경험자의 피드백은 분리해서 읽습니다.** TD는 세션이 긴 장르라 경험자는 3~4분짜리 판을 "짧다"고 느낍니다. 그건 설계 실패가 아니라 [`game-design.md`](game-design.md) 1절에서 의도적으로 고른 방향입니다. 반대로 비경험자가 "길다"거나 "뭘 해야 할지 모르겠다"고 하면 그건 고쳐야 할 신호입니다. 두 집단의 같은 단어가 반대 뜻입니다. 근거는 [`tower-defense-research.md`](tower-defense-research.md) 6절.

**완료 기준**: 5명의 위 항목이 기록되고, 재도전율과 첫 이탈 지점이 나온다.

### 2. 저사양 안드로이드 실기기 측정 — 기기가 생기면 즉시

**왜 지금 못 하나**: 안드로이드 단말이 없습니다. 이것 하나뿐입니다.

**방법**: 폰 브라우저로 `배포URL/?perf` 를 엽니다. 계정도, 빌드도, 업로드도 필요 없습니다. Firebase Test Lab은 여러 기종을 자동·반복 측정할 때나 의미가 있고 PoC에는 과합니다.

**측정 절차**
1. 기본값(40/18/8)에서 판정 줄을 읽는다
2. 슬라이더를 **200 / 60 / 40** 으로 올린다 (스프라이트 약 560개 = 목표 규모 상한)
3. **그 상태로 3~4분 방치 후 다시 읽는다** — 발열 스로틀링은 세션 길이가 있어야 나타나고, 데스크톱·에뮬레이터로는 재현 불가

**확인할 것**
- `draws` 가 2에서 안 움직이는지 (오르면 나머지 수치 전부 무효)
- `work p95` 는 평탄한데 `frame p95` 만 오르는지 → GPU fill-rate 병목
- `heap` 평탄 여부
- 시작 직후 대비 3분 뒤 `work p95` 차이

**완료 기준**: 실기기 기준 `(엔티티 수 → p95)` 표가 `m0-measurements.md` 에 들어가고, 연출 상한이 확정된다.

**실패 시**: 내부 해상도를 먼저 낮추고, 그래도 안 되면 파티클 수를 줄입니다. 아트 방향은 마지막에 건드립니다.

### 3. 밸런스 — 관찰 데이터가 나온 뒤

두 가지가 알려져 있고, 사실상 같은 문제입니다.

- **한 판이 5분대** (목표 3~4분). 준비 시간을 건너뛰면 4분 근처지만 기본값이 깁니다.
- **곡선이 뒤로 치우침**. 최적 배치 기준으로 웨이브 1~8이 무손실이고 데미지가 9~10에 몰립니다.

**손댈 곳**: `src/content/waves.ts` 의 `hpScale`, `reward`, 스폰 `interval`, `PREPARE_SECONDS`.

**하지 말 것**: 손으로 플레이하며 감으로 조정. `npx vitest run src/core/balance-report.test.ts` 로 격자를 다시 뽑아 판단합니다.

**완료 기준**: 한 판 3~4분, 첫 체력 손실이 웨이브 5~6쯤, 봇 기준 승리 시 잔여 체력 40~70.

### 4. 로스터 컨셉 고도화 — 별도 트랙 (haneul님)

현재 적·타워 이름과 성격은 즉흥안입니다. 확정되면 `src/content/enemies.ts` / `towers.ts` 교체로 반영되고, 코드는 손대지 않습니다.

**설계에 영향을 주는 제약** (컨셉을 잡을 때 알아두면 좋은 것)
- 적은 4종 안팎이 적당합니다. 팔 길이에서 픽셀아트로 구분돼야 합니다.
- 타워는 4종, 초반에 2~3종만 열립니다. 초보자에게 선택지 3개가 상한입니다.
- 적 이름이 "막아야 할 것"으로 즉시 읽히면 튜토리얼 비용이 사라집니다. 지금 로스터의 가장 큰 장점이 이것입니다.
- 타워는 적의 대응물로 읽히는 게 좋습니다(수면부채 ↔ 수면).
