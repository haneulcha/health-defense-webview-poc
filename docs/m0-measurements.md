# M0 — 프레임 예산 측정

## 이 문서가 말하지 않는 것

**여기 있는 절대 수치로 저사양 안드로이드 성능을 판단하면 안 됩니다.** 아래 표는 macOS의 헤드리스 Chrome에서 잰 것이고, 실기기가 아직 없습니다. GPU fill-rate, 메모리 대역폭, 발열 스로틀링 중 어느 것도 재현되지 않았습니다.

절대치가 아니라 **구조적 결론**과 **회귀 감지 기준선**으로만 쓰십시오. 실기기 측정(Firebase Test Lab / Samsung Remote Test Lab)이 남은 작업입니다.

## 방법

- 합성 벤치가 아니라 **실제 렌더 경로**를 측정합니다. 실제 엔티티, 실제 아틀라스, 실제 HUD. 무작위 스프라이트 벤치의 숫자는 draw order·텍스처 구성·프레임당 로직이 달라 게임에 전이되지 않습니다.
- 두 가지를 따로 잽니다.
  - `frame p95` — 프레임 간 벽시계 시간. 프레임 드랍은 보이지만 **여유는 보이지 않습니다**. vsync에 묶이면 항상 주사율과 같은 값이 나옵니다.
  - `work p95` — `sim.step + scene.sync + renderer.render`에 실제로 쓴 시간. **여유를 재는 건 이쪽입니다.**
- 예산은 고정 16.7ms가 아니라 **실측 주사율**에서 계산합니다. 90/120Hz 패널에서 rAF는 패널 주사율로 뜁니다.
- 스트레스 하네스는 죽은 적을 **경로 위 임의 지점**에 재배치합니다. 입구에 재스폰하면 적이 상단에 뭉쳐 아래쪽 타워가 전부 놀고, 동시 발사체가 실제의 1/5로 측정됩니다.

### 재현

```bash
npm run dev     # 그리고 http://localhost:5173/?perf
```

하네스는 게임 번들에 그대로 들어 있습니다. 실제 렌더 경로를 재기 때문에, 게임이 도는 어떤 기기에서든 — 데스크톱 프로파일러가 닿지 않는 RN WebView 안에서도 — 쿼리 파라미터 하나로 같은 측정을 다시 할 수 있습니다.

브라우저 콘솔에서 `window.__harness` 로 스윕을 자동화합니다.

```js
const h = window.__harness
h.setControls({ enemies: 120, towers: 45, particlesPerKill: 20 })
// 1.5초 안정화 → h.resetMetrics() → 4초 수집 → h.read()
```

## 실기기 — iPhone 17 (2026-08-11)

최대 부하(적 200 / 타워 60 / 파티클 40, 스프라이트 약 560개)에서:

| 지표 | 값 |
|---|---|
| 예산 사용률 | **12%** (60Hz → 16.7ms) |
| draws | 2 (엔티티 수와 무관하게 고정) |

**이 수치로 저사양 안드로이드를 판단하면 안 됩니다.** iPhone 17은 현재 가장 빠른 축이고, 저가 안드로이드와는 GPU fill-rate·메모리 대역폭에서 몇 배 차이가 납니다. 이건 천장이지 예산이 아닙니다.

의미 있는 결론은 두 가지입니다.

1. **WKWebView는 비쟁점입니다.** iOS는 JIT 제약과 Safari 특유 이슈 때문에 실제 열린 질문이었는데, 8배 여유면 접어도 됩니다.
2. **배칭이 실기기에서도 유지됩니다.** 헤드리스 Chrome에서만 확인했던 `draws=2`가 실제 하드웨어에서 재현됐습니다.

발열 테스트는 이 기기에서 생략했습니다 — 12%에서는 스로틀링이 걸려도 예산을 넘길 수 없어 측정 가치가 없습니다.

**저사양 안드로이드는 아직 미측정입니다.** 배포 URL을 안드로이드 단말에서 열면 그대로 측정됩니다.

## 데스크톱 기준선 (2026-08-10)

헤드리스 Chrome, 뷰포트 360×800 DPR 1, 실측 주사율 120Hz → 예산 8.3ms.

| 적 | 타워 | 발사체 | 파티클 | 총 스프라이트 | work p95 | work p99 | draws | heap |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 0 | 0 | 0 | 0.10ms | 0.20ms | 2 | 21MB |
| 20 | 10 | 2 | 5 | 37 | 0.20ms | 0.40ms | 2 | 20MB |
| 40 | 18 | 7 | 6 | 71 | 0.30ms | 0.40ms | 2 | 20MB |
| 80 | 30 | 12 | 19 | 141 | 0.40ms | 0.60ms | 2 | 21MB |
| 120 | 45 | 21 | 43 | 229 | 0.50ms | 0.90ms | 2 | 21MB |
| 200 | 60 | 31 | 168 | 459 | 0.80ms | 1.20ms | 2 | 21MB |

`frame p95`는 모든 행에서 9.1~9.2ms로 일정했습니다. 즉 루프는 전 구간에서 vsync 대기 상태였고, 계산 부하가 프레임을 밀어낸 적이 없습니다.

## 구조적 결론 (실기기와 무관하게 유효)

1. **draw call이 엔티티 수와 무관하게 2로 고정.** 스프라이트 아틀라스 배칭이 의도대로 동작합니다(지형 캐시 1 + 나머지 전부 1). 이 값이 엔티티 수를 따라 올라가기 시작하면 배칭이 깨진 것이고, 그때 성능표는 전부 무효가 됩니다. **회귀 감시 대상 1순위.**
2. **heap이 20~21MB에서 평탄.** 발사체·파티클 풀링이 동작해 정상 상태에서 할당이 발생하지 않습니다. 저사양 안드로이드 WebView의 최대 렉 원인인 GC 스파이크가 구조적으로 차단됩니다.
3. **work 시간이 스프라이트 수에 대략 선형**이며 급격한 무릎 지점이 없습니다. 목표 규모(스프라이트 ~510)는 이 곡선의 마지막 행 근처입니다.

## 아직 답하지 못한 것

- **GPU fill-rate.** 백킹스토어를 168×312로 고정해 구조적으로 상한을 걸었지만, 실제 저사양 GPU에서 업스케일 합성 비용이 얼마인지는 측정되지 않았습니다.
- **발열 스로틀링.** 3~4분 세션의 **마지막 웨이브** p95를 재야 하며, 데스크톱에서는 의미가 없습니다.
- **WKWebView.** iOS 시뮬레이터는 진짜 WebKit을 돌리므로 오디오 언락·바운스·rAF 동작 검증에 쓸 수 있습니다. 성능은 무의미합니다.
- **저전력 모드의 WKWebView는 rAF를 30fps로 스로틀합니다.** 테스터가 30fps를 보고해도 성능 문제로 오진하지 마십시오.

## 알려진 한계

- 개발 하네스 HUD는 최소 HUD 밴드(96px)보다 내용이 많아 짧은 화면에서 스크롤됩니다. 실제 게임 HUD(타워 버튼 + 상태)는 96px에 맞춰 설계되어 있습니다.
- `work` 시간은 CPU 측만 잽니다. GPU 작업은 비동기로 끝나므로, fill-rate 병목은 **work는 평탄한데 frame p95만 오르는** 형태로 나타납니다. 두 수치를 같이 읽어야 합니다.
